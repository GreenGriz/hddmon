# Спецификация: hddmon — мониторинг и прогноз состояния HDD

Статус: спецификация согласована, открытые вопросы закрыты (§9), реализация в процессе.
Дата: 2026-10-16.

## 1. Цели

- Снимать SMART-состояние всех дисков машины.
- Определять здоровье по ключевым параметрам (хранить всё подряд без смысла не нужно).
- Хранить историю снимков для выявления динамики.
- Выдавать прогноз: какой диск бэкапить, какой менять, с объяснением причин.

## 2. Способы чтения SMART (варианты)

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **`smartctl -j -a`** (smartmontools) | де-факто стандарт, JSON-вывод (7.x), ATA/SCSI/NVMe, логи self-test и ошибок | нужен root | **Рекомендация** |
| smartd (уже запущен) | события в реальном времени | не даёт истории/аналитики | как источник событий/алармов |
| udisks2 D-Bus / hddtemp | без root | мало атрибутов, устарело | нет |
| библиотеки (pysmart и т.п.) | обёртка | всё равно зовут smartctl | не нужна |

**Решение:** коллектор вызывает `smartctl -j -a <dev>`, парсит JSON; автоопределение типа устройства с фоллбэком (`-d ata` → `-d scsi` → `-d nvme`), т.к. на этой машине scan отдаёт `-d scsi`, но диски SATA. Запуск от root (systemd unit) либо точечное sudoers-правило на smartctl.

## 3. Наиболее важные параметры

### ATA/SATA (основной случай этой машины)

| ID | Атрибут | Значение |
|---|---|---|
| **5** | Reallocated_Sector_Ct | **Критично**: растёт = деградация поверхности |
| **197** | Current_Pending_Sector | **Критично**: секторы ждут переноса |
| **198** | Offline_Uncorrectable | **Критично** |
| **187** | Reported_Uncorrect | **Критично** |
| **184** | End-to-End_Error | важно (контроль целостности кэша) |
| **188** | Command_Timeout | важно |
| **189/183/178** | High_Fly_Writes / GMR / Wear (Seagate) | важно |
| **194** | Temperature | перегрев >45–50 °C ускоряет износ |
| **9** | Power_On_Hours | возраст |
| **12** | Power_Cycle_Count, **193** Load_Cycle_Count | ресурс механики |
| **192** | Unsafe_Shutdown (SSD), **241/242** LBAs Written/Read | нагрузка/износ SSD |

Также: overall-health PASSED/FAILED + exit-код smartctl, лог self-test (attribute 0x07), лог ошибок (attribute 0x03) — сводная оценка.

### SCSI (сейчас smartctl так видит диски)

Grown defect count, счётчики ошибок read/write/verify (`-l error`), temperature, power-on hours, результаты self-test.

### NVMe (на будущее)

critical_warning, percentage_used, available_spare, media_errors.

**Рекомендация по хранению — гибрид:** в колонках снимка — только ключевые (см. §5) для быстрых запросов и графиков; **все** атрибуты — в нормализованной таблице (это копейки: ~30 строк × 4 диска × раз в день). Полный raw-JSON smartctl — опционально, с ретенцией (напр., 90 дней).

## 4. Хранилище (варианты)

| Вариант | Когда | Вердикт |
|---|---|---|
| **SQLite** | один хост, встроено в Python 3.11 (3.40.1), ноль сервисов, бэкап = копия файла | **Рекомендация** |
| CSV/JSONL-файлы | максимальная простота | плохо для истории/трендов/запросов — как экспорт, не основа |
| Prometheus + Grafana | живые графики/алерты | история/прогноз неудобны, тяжелее |
| PostgreSQL / TimescaleDB | централизованный мониторинг нескольких машин | отложить до появления второй машины |

### Схема (SQLite)

```sql
devices(id, dev_node, model, serial UNIQUE, transport, capacity, first_seen, last_seen)

snapshots(
  id, device_id, taken_at,
  smart_passed,
  temperature, power_on_hours,
  reallocated, pending, uncorrectable, reported_uncorrect, load_cycle,
  selftest_status,
  verdict, score,
  raw_json
)

attributes(snapshot_id, device_id, attr_id, name, raw_value, normalized, worst, failed)

events(id, device_id, at, type, severity, message)
-- события: смена вердикта, рост критичного атрибута, selftest fail
```

## 5. Модель оценки (verdict)

- **REPLACE_NOW / BACKUP_NOW** — selftest FAILED или overall FAIL; растущие 5/197/198/187 > 0; >X pending секторов.
- **BACKUP_SOON** — атрибуты > 0, но стабильные; быстрый рост ошибок/таймаутов; температура стабильно > 45 °C.
- **WATCH** — возраст/наработка на пределе, рост load cycles, температурные пики.
- **OK** — отклонений нет.

Оценка — пороговая + **дельты между снимками** (именно динамика, а не абсолютное значение, отличает «умирающий» диск от «так было всегда»).

## 6. Прогноз

1. **Уровень 1 (MVP):** правила из §5 + объяснение причин.
2. **Уровень 2:** линейная регрессия по критичным атрибутам → скорость деградации и ETA «когда станет REPLACE_NOW»; учёт температурной истории (правило «−8 °C ≈ ×2 срок службы» как эвристика) и наработки.
3. Отчёт: `hddmon status` / `history <disk>` / `predict` / `report --json`; exit-коды для интеграции с мониторингом.

## 7. Архитектура и выполнение

- **Python 3.11**, только stdlib (sqlite3, subprocess, json, argparse, tomllib) — без внешних зависимостей.
- Компоненты:
  - `collector` — smartctl → JSON (авто-тип с фоллбэком, smartctl напрямую от root или через `sudo -n`);
  - `normalizer` — единая модель ATA/SCSI/NVMe;
  - `analyzer` — вердикты, дельты, тренды;
  - `store` — SQLite (схема с версией в `meta`, миграции);
  - `forecast` — линейная регрессия критичных атрибутов → ETA;
  - `notify` — опциональные Telegram и email;
  - `cli` — интерфейс.
- Хранение: **гибрид** — ключевые атрибуты колонками в `snapshots` (для трендов/прогноза) + все атрибуты в `attributes` (~3–5 МБ/год при съёмке раз в сутки). Raw JSON — только опциональным флагом.
- Диски: заводятся/заменяются автоматически по серийнику; пропавший диск помечается `present=0`, история сохраняется.
- Запуск: systemd timer (system — от root, либо user — с sudoers на smartctl); флаг `--store-raw` для raw JSON.
- Уведомления (опционально, каждый канал независимо): Telegram (bot token + chat_id), email (SMTP). Шлются при переходе в BACKUP_SOON/BACKUP_NOW/REPLACE_NOW, росте критичных атрибутов, исчезновении диска.
- UI: CLI (status/smart/history/predict/report/devices). Web-интерфейс — возможно позже, не в MVP.
- Exit-коды `status`/`report`: 0=OK, 10=WATCH, 20=BACKUP_SOON, 30=BACKUP_NOW, 40=REPLACE_NOW, 1=ошибка.

## 8. Приёмка

- smartctl доступен без правок;
- снимок по всем 4 дискам;
- история накапливается;
- `status` даёт вердикт с причинами;
- алгоритм честно ранжирует уже деградирующие диски (5/197/198 > 0).
